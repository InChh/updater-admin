# Exploration Findings

## Dispatch 1 — Current upload, version association, and public manifest seams

### Findings

- **Folder selection / cap**: `src/features/versions/folder-picker.tsx:62-91` converts the directory `FileList` into normalized, sorted relative paths, rejects oversized files and more than `MAX_UPLOAD_FILES`; `:145-150` sets `webkitdirectory`/`directory`. The cap comes from `src/shared/api/uploads.ts:2-18`, where `MAX_UPLOAD_FILES = VERSION_FILES_MAX_ITEMS`, currently `5_000` in `src/shared/api/versions.ts:6-11`. `src/features/versions/version-form.tsx:136-152,232-245` repeats the 5,000-file validation before upload and final submission.
- **Hashing / upload**: `src/features/versions/hash-worker.ts:3-5,115-140` hashes incrementally in 4 MiB slices; `src/features/versions/upload-workflow.client.ts:37-44,247-274,802-813` bounds hashing to 2 workers and file uploads to 4. `src/features/versions/oss-uploader.client.ts:300-304,347-412` uses a fresh cancellable OSS client per file, multipart parallelism 2, in-memory checkpoints, and `x-oss-forbid-overwrite: true`.
- **Object keys**: `src/server/integrations/oss/object-key.ts:33-61` derives `${normalizedPrefix}${sha256}/${percentEncodedPath}`, preserving `/`, and enforces the 1,023-byte OSS key limit. Server credential issuance validates every deterministic target before STS in `src/server/domain/uploads.server.ts:268-303,610-645`.
- **Credential behavior**: the browser retains only one `UploadAuthorization`. It reuses it while expiration is more than 60 seconds away and every requested path/fingerprint/object target is already in that authorization (`src/features/versions/upload-workflow.client.ts:236-245,421-477`). Ready files are sliced into 1,000-file credential batches (`:675-693`), so a folder over 1,000 receives a new API response and STS AssumeRole call per batch; the current test confirms `[1000, 1]` requests (`src/features/versions/upload-workflow.client.test.ts:286-313`). Near-expiry retry refresh is covered at `:561-626`.
- **Retry model**: application-level retry is explicit per failed/cancelled item, stage-aware, preserves multipart checkpoints, and can reconcile an ambiguous committed upload through completion HEAD before re-upload (`src/features/versions/upload-workflow.client.ts:620-661,763-800`). No workflow-level automatic backoff loop is present.
- **STS policy/API**: the temporary policy is already prefix-wide, not object-list-specific: only `oss:PutObject` and `oss:AbortMultipartUpload` on `acs:oss:*:*:<bucket>/<prefix>*` (`src/server/integrations/oss/sts.server.ts:11-14,162-185`). Each call performs a fresh 900-second AssumeRole request and validates the returned credentials (`:242-298`). The metadata-only request and response—including temporary keys, expiration, bucket/region, and deterministic targets—are defined in `src/shared/api/uploads.ts:45-83`; transport limits are 1,000 files/targets in `src/server/api/modules/uploads.ts:50-113`; the authenticated no-store endpoint is `:318-331`. Issuance is limited to 10 requests per 5 minutes per administrator at `src/server/api/plugins/rate-limit.server.ts:42-50`.
- **Completion / persistence**: browser completion batches are sequential chunks of 25 (`src/features/versions/upload-workflow.client.ts:578-618`), enforced again by the API schema (`src/server/api/modules/uploads.ts:115-150`). Each request is charged by file count and limited to two concurrent requests per actor per function instance (`:205-239,333-385`). Server HEAD-verifies canonical key, exact byte size, and optional submitted ETag with concurrency 4 (`src/server/domain/uploads.server.ts:449-525,538-608`); the permanent RAM OSS client is used at `src/server/integrations/oss/client.server.ts:129-170`.
- **Idempotency / transactions**: `file_metadata` has a live unique identity on `(path, sha256, size)` (`src/server/db/schema/business.ts:108-147`). Completion sorts identities to avoid reversed-batch deadlocks, performs insert-on-conflict/no-op plus locked replay comparison, restores caller order, and appends `upload.completed` in the same transaction (`src/server/db/repositories/uploads.server.ts:103-158,160-214`). Replays must also match MIME type, object key, and ETag (`:86-100`).
- **Version association contract/model**: `version_files` is a `(version_id, file_metadata_id)` join-table primary key (`src/server/db/schema/business.ts:150-165`). Create requires a non-empty full `fileIds` array; PATCH is tri-state—omitted preserves, `[]` removes, populated replaces (`src/shared/api/versions.ts:39-67`). The browser sends the entire set in one request (`src/features/versions/api.ts:68-100`), and transport/domain both cap it at 5,000 (`src/server/api/modules/versions.ts:59-143`; `src/server/domain/versions.server.ts:211-243`).
- **Version transaction / audit / ETag**: create locks the program, checks version monotonicity and every live file ID, inserts the version and all relations, calculates the detail, and audits the complete result in one transaction (`src/server/db/repositories/versions.server.ts:496-554`). Update locks program/version, checks row version, reads the full old relation set, validates the full replacement through one `IN (...)`, deletes/reinserts all relations, increments row version, and audits full before/after sets atomically (`:390-435,722-807`). HTTP responses expose standard `ETag`; mutations consume only `X-Updater-If-Match` (`src/server/api/modules/versions.ts:311-365`; `src/server/api/preconditions.ts:4-14`; `src/shared/api/common.ts:5-9,55-67`).
- **Public manifest**: anonymous routes are `/api/public/v1/programs/:programId/releases/latest` and `/:versionNumber` (`src/server/api/modules/public-releases.ts:102-134`), mounted outside the administrator group (`src/server/api/app.server.ts:133-167,200-210`). The repository selects the highest active semantic version, joins all live related files in path/id order, and fetches up to `5_001` rows to enforce the 5,000 invariant (`src/server/db/repositories/public-releases.server.ts:68-116,119-173`). The service signs every object individually with concurrency 8 and a 300-second GET TTL (`src/server/domain/public-releases.server.ts:43-99`); the response omits DB IDs, object keys, ETags, and credentials (`src/shared/api/public-releases.ts:1-23`). Public requests are no-store and IP-limited to 120/minute (`src/server/api/plugins/public-api.server.ts:20-29,95-170`).
- **Documentation drift**: `README.md:130-132` still claims public manifests contain at most 256 files, while the executable shared/API/domain/repository limit is 5,000. Treat 5,000 as current code behavior and the README as stale.
- **Tests/config**: key coverage includes folder caps/path validation (`src/features/versions/folder-picker.test.tsx:22-66`), upload batching/expiry/concurrency/retry (`src/features/versions/upload-workflow.client.test.ts:250-313,561-626,835-948`), STS scope/900-second issuance (`src/server/integrations/oss/sts-client.test.ts:57-198`), HEAD and atomic completion (`src/server/domain/uploads.test.ts:314-438`; `src/server/db/repositories/uploads.server.db.test.ts:70-133`), version relation tri-state/rollback/ETag races (`src/server/db/repositories/versions.server.db.test.ts:268-372,488`), and public cap/signing concurrency (`src/server/domain/public-releases.test.ts:176-235`). Runtime OSS inputs are read in `src/server/env.server.ts:256-274`; `.env.example:51-57` declares their names. `netlify.toml:1-12` sets Node 22/esbuild but no explicit function timeout or memory override.

### Relationships

`FolderPicker` → in-memory upload queue → bounded hash workers → 1,000-file credential/target batches → direct multipart OSS upload → 25-file completion batches → bounded server HEAD verification → idempotent `file_metadata` persistence → full `fileIds` version create/PATCH → `version_files` relations → public joined manifest → per-file signed GET URLs.

### Minimum change surface

- **No total file-count cap**: the directly coupled cap owners are `src/shared/api/versions.ts`, `src/shared/api/uploads.ts`, `src/features/versions/folder-picker.tsx`, `src/features/versions/version-form.tsx`, `src/server/api/modules/versions.ts`, `src/server/domain/versions.server.ts`, `src/server/api/modules/public-releases.ts`, `src/server/domain/public-releases.server.ts`, `src/server/db/repositories/public-releases.server.ts`, and `src/server/api/plugins/rate-limit.server.ts`, plus their localized labels/tests. Removing only the constant check would leave unbounded request/response/audit/SQL arrays.
- **One STS credential set per validity window**: minimum affected contracts are `src/shared/api/uploads.ts`, `src/features/versions/upload-workflow.client.ts`, `src/server/api/modules/uploads.ts`, `src/server/domain/uploads.server.ts`, and potentially `src/server/integrations/oss/sts.server.ts` if credential reuse ownership lives server-side. Current policy scope already permits reuse; the blocking coupling is that target derivation and AssumeRole issuance share one 1,000-file API call and the browser retains only one batch’s target map. Rate-limit/audit semantics and tests also change.
- **Bounded metadata batches**: upload completion is already bounded at 25 across browser, wire, domain, and repository. The remaining unbounded seam after cap removal is version association/finalization: `src/shared/api/versions.ts`, `src/features/versions/api.ts`, `src/server/api/modules/versions.ts`, `src/server/domain/versions.server.ts`, and `src/server/db/repositories/versions.server.ts`.
- **Scalable version finalization/public manifest**: the minimum version surface is the full-array create/PATCH/detail contract and relation/audit transaction above. The minimum public surface is `src/shared/api/public-releases.ts`, `src/server/api/modules/public-releases.ts`, `src/server/domain/public-releases.server.ts`, `src/server/db/repositories/public-releases.server.ts`, and public tests/plugin route matching if the wire shape or route structure changes.

### Impact

- **Scope**: cross-module.
- **Primary risks**: Netlify request/response duration and buffering; PostgreSQL parameter/statement size from full `IN` and bulk inserts; transaction duration and lock contention; audit JSON growth from full file sets; repeated STS issuance hitting the 10-per-5-minute policy; thousands of signed URL operations per anonymous request; memory growth from retaining every `File`, queue row, file ID, joined DB row, and signed response simultaneously.
- **Integrity boundary**: server verification checks canonical key, size, and ETag, not object contents against SHA-256; integrity also relies on browser hashing, deterministic keys, and overwrite prohibition. That boundary becomes more consequential as batch counts grow.
- **Evidence boundary**: current tests prove bounded correctness through just over 1,000 upload targets, 53 completion items, and a small signing-concurrency set; there is no uncapped-folder, large finalization, or large public-manifest load test.

### Next Steps

- Ready for technical design; no code changes were made.

## Dispatch 2 — Draft lifecycle, migration, UI sequence, audit, and verification seams

### Findings

1. **Version table/semantics**: `src/server/db/schema/business.ts:44-106` — columns are identity/application FK, semantic-version text/components, description, `is_active default false`, audit timestamps/users, soft-delete fields, and `row_version default 1`; live semantic versions are unique, while no single-active or draft/status constraint exists. `src/server/db/repositories/versions.server.ts:366-388,437-447` — `isLatest` is derived as the highest active, non-deleted semantic version. `src/server/db/repositories/versions.server.ts:664-720` — activation updates only the addressed row, so multiple active versions are supported. Public latest uses the same active/live descending selection in `src/server/db/repositories/public-releases.server.ts:68-116`.
2. **Migration/schema tests**: `drizzle/meta/_journal.json:1-20` and `drizzle/0001_blushing_giant_man.sql:1-2` — numbered generated SQL names, journal tags, snapshots, and `statement-breakpoint` separators. `drizzle.config.ts:1-16` — PostgreSQL Drizzle config, schema entrypoint `src/server/db/schema/index.ts`, output `drizzle/`. Schema shape/index assertions are in `src/server/db/schema/schema.test.ts:224-393`; live-DB/default validation starts in `src/server/db/schema/schema.db.test.ts:25-62,139-157`.
3. **Create-version dialog sequence**: `src/features/versions/version-form.tsx:232-245` folder selection clears/replaces the queue and adds validated files → `src/features/versions/version-form.tsx:465-514` renders queue and starts upload → `src/features/versions/version-form.tsx:224-231` awaits workflow completion → `src/features/versions/version-form.tsx:133-165,545-569` collects completed metadata IDs and submits → `src/features/versions/api.ts:68-79` POSTs `{description,fileIds,versionNumber}` → `src/features/versions/version-dialogs.client.tsx:340-355` invalidates queries, notifies, and closes → `src/features/versions/versions-page.tsx:130-131,386-390` removes dialog state from the URL.
